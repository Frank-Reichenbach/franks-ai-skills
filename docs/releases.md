# Releases

This repo currently is one plugin (`frank`), so it gets one version:

- `plugin.json` (`version`) and the `frank` entry in `.claude-plugin/marketplace.json` (`version`) are bumped together and follow [SemVer](https://semver.org/); `tools/checks.py` fails the build if they disagree or either one isn't SemVer. A version string is what Claude Code's plugin installer compares to detect an update — an already-installed copy is skipped while it matches.
- **Which of the two Claude Code reads here matters, because the two fields are not interchangeable.** For every source type except `command`, Claude Code resolves a plugin's version from the first of these that is set: the plugin manifest's `version`, then the marketplace entry's `version`, then the git commit SHA of the source (which covers this repo — a relative-path source in a git-hosted marketplace), then an archive digest, then `unknown`. The manifest it means is `.claude-plugin/plugin.json` — and this repo has no such file. Its root-level `plugin.json` is an Agent Plugins 1.0 manifest at a different path, which is not the file that order names (see `docs/portability.md`). So for Claude Code the **marketplace entry's `version` is the operative field**: never drop that one. Dropping it would silently demote update detection to commit-SHA tracking, where every pushed commit reads as a new version. `checks.py` requires this field.
- **Codex reads the root `plugin.json`'s `version` instead.** It uses the root file as the plugin's manifest (see `docs/portability.md`), names the installed copy's cache folder after that version, and reinstalls only when the version string changes — an unchanged version keeps serving the old cached copy (source: `openai/codex`, `core-plugins/src/loader.rs`, the `IfVersionChanged` refresh). A missing version defaults to `1.0.0`, so it would never change. Each client reads a different field, so both are required and must match; `checks.py` enforces both.
- Tagging is optional and this repo has no tags. Git tags play no part in the resolution order above — they are not one of its steps. Claude Code uses tags for a different job: resolving a *dependency's* version constraint, when another plugin declares a dependency on this one. That needs the `{plugin-name}--v{version}` naming convention (`frank--v0.1.1`), not a bare `v0.1.1`. `claude plugin tag` generates that name — but not against this repo's layout. Verified on Claude Code 2.1.281, in a clean clone: the command resolves the plugin root to the *parent* directory and aborts with `<parent> is not inside a git repository`. Adding a metadata-only `.claude-plugin/plugin.json` makes it resolve correctly and plan `frank--v0.1.1`; removing it brings the failure straight back. Nothing declares a dependency on `frank` today, so there is nothing to tag for and nothing to fix. If that workflow is ever adopted, adding that manifest is the prerequisite — and note it would also become the first step of the resolution order above, displacing the marketplace entry as the operative field.
- No per-skill versioning. Git history is a skill's version history.

Once a second plugin exists, each distributable plugin gets its own SemVer instead of one repo-wide version. Introduce per-skill versioning only if a specific skill becomes an independently published artifact outside this repo.

## CI

`.github/workflows/validate.yml` runs `tools/validate.sh` on every pull request: the `tools/tests` unit test suite, `claude plugin validate . --strict`, a structural check on `plugin.json` and `.claude-plugin/marketplace.json` (name/version/description shape, both versions present and SemVer, `license`/`repository`/`owner.url` shape if present, `strict`/`skills` field types, and that the two manifests agree on version and on the set of skills), a frontmatter lint on every `SKILL.md`, and a structural check on `evals/<skill>/routing.yaml`, `evals/<skill>/behavior.yaml` and any `evals/<skill>/behavior-<scenario>.yaml` for every skill under `skills/`, plus `evals/catalog/collisions.yaml`. These are deterministic and free — no API key required.

Both `SKILL.md` frontmatter and the eval files are parsed with a real YAML parser (PyYAML — see `tools/requirements.txt`), not hand-rolled pattern matching. An earlier version tried to get away with regex-based parsing to avoid the dependency; two rounds of review found real, reproducible gaps in it (block scalars, null literals, and comments all had cases that either passed invalid content or rejected valid content), which is exactly the class of bug a real parser doesn't have. Genuinely malformed YAML in either a `SKILL.md`'s frontmatter or an eval file is now rejected, not silently accepted.

A skill's optional `evals/<skill>/behavior-<scenario>.yaml` files (for judgment-heavy decision points — see `skills/skill-writing/SKILL.md`) are checked for the same structure as `behavior.yaml`.

Behavioral evaluation (actually running `evals/<name>/routing.yaml`, `behavior.yaml` and `behavior-<scenario>.yaml` against a live model, for example via `anthropics/claude-code-action`) is intentionally not wired up yet. It needs an `ANTHROPIC_API_KEY` repository secret and has a real per-run cost; add it as a separate change when that trade-off is worth making.
